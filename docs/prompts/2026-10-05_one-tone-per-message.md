## 프롬프트 원문

```
CLAUDE.md 규칙대로, 가짜 AI(ai.js)가 만드는 메시지 한 통 안에 해요체·합니다체·반말이 섞이는 문제를 고치자.
원인은 앱이 붙이는 문장(인사·연결·끝인사)만 끝맺음을 맞추고, 사용자가 칸에 쓴 문장의 끝맺음은 그대로 두기 때문이야.
먼저 지금 코드에서 끝맺음이 어디서 정해지는지 쉬운 말로 설명하고, 바꿀 방식을 보여 준 뒤 내 승인을 받아.

[원칙: 메시지 한 통 = 문체 하나]
1. 메시지를 만들 때 문체를 먼저 하나로 정한다.
   - 클라이언트: 합니다체 고정
   - 동기: 반말 고정 (코딩 레퍼런스 2장 6절 "반말 허용". 팀 확정 전 임시안이니 decision-log에 '확인 필요'로 기록)
   - 선배·인차지: 내 말투 설정의 끝맺음(hamnida → 합니다체, haeyo → 해요체)
2. 문장을 다 조립한 뒤 마지막 단계에서 모든 문장을 나눠 끝맺음을 검사하고, 정한 문체로 바꾼다.
   사용자가 쓴 칸 값, 앱이 붙인 문장, 탭 3종(내 말투안·더 간결하게·더 부드럽게) 모두에 적용한다.
   '더 간결하게'의 항목형 줄(예: "- 기한: 내일 오전 10시까지 제출")처럼 문장이 아닌 줄은 바꾸지 않는다.
3. 끝맺음 변환 표를 content.js에 한곳으로 모아 줘(나중에 추가하기 쉽게). 최소한 아래는 포함:
   · 평서문 : 했습니다 ↔ 했어요 ↔ 했어 / 합니다 ↔ 해요 ↔ 해 / 입니다 ↔ 이에요·예요 ↔ 이야·야
             있습니다 ↔ 있어요 ↔ 있어 / 없습니다 ↔ 없어요 ↔ 없어 / 됩니다 ↔ 돼요 ↔ 돼
             생각합니다 ↔ 생각해요 ↔ 생각해 / 어렵습니다 ↔ 어려워요 ↔ 어려워 / 드리겠습니다 ↔ 드릴게요 ↔ 줄게
   · 요청문 : 부탁드립니다 ↔ 부탁드려요 ↔ 부탁해 / 주시기 바랍니다·주십시오 ↔ 주세요 ↔ 줘
   · 의문문 : 되겠습니까?·될까요? ↔ 될까요?·되나요? ↔ 될까?·돼? / 있습니까? ↔ 있나요? ↔ 있어?
             주실 수 있을까요? ↔ 주실 수 있나요? ↔ 줄 수 있어?
   · 메모체 : ~함 / ~음 / ~임 / ~됨 → 정한 문체의 평서문으로
   합니다체 의문문은 "~습니까?"와 "~ㄹ까요?" 중 무엇을 쓸지 예시 3개씩 보여 주고 내 선택을 받아.
   (직장 메신저에서는 "~ㄹ까요?"를 합니다체와 함께 쓰는 경우가 많아서 확인하려는 거야)
4. 변환 표에 없는 끝맺음이 나오면 억지로 바꾸지 말고, 점검 도구에 '변환 못 한 끝맺음'으로 표시해 줘. 그 목록을 보고 표를 늘릴 거야.
5. 끝맺음만 바꾸고 내용(날짜·시간·숫자·마스킹·요청 대상·질문 내용)은 절대 바꾸지 않는다.
   질문 준비실 마지막 문장('묻고 싶은 것', B2)도 끝맺음만 바꾼다.
6. 의도 체크 근거 구절은 끝맺음을 바꾼 뒤에도 본문에 글자 그대로 있게 한다(끝맺음 앞부분까지만 근거로 쓰기).
7. 앱 안내 문구(화면 문구·수정 이유·토스트)는 메시지와 별개로 해요체로 통일한다(코딩 레퍼런스 2장 1절).
   수정 이유 안에 해요체와 합니다체가 섞여 있으면 같이 고쳐 줘.

[점검]
- scripts/check-messages.mjs가 있으면 아래 항목을 추가하고, 없으면 이 항목만으로 간단히 만들어 줘
  (ai.js를 Node vm으로 불러와 data/cards.json, data/malgyeol_sample_data.json으로 실행).
  · 메시지마다 문장 끝을 분류해서 정한 문체와 다른 문장이 하나라도 있으면 '문체 혼합'으로 표시
  · '변환 못 한 끝맺음' 목록
  · 수정 이유(앱 안내 문구)에 해요체가 아닌 문장이 있는지
- 대상: 샘플 30건 × 탭 3종 × 받는 사람 4종 × 끝맺음 2종. 고치기 전과 후의 '문체 혼합' 개수를 표로 비교해 줘.
- 목표: 문체 혼합 0건. 남는 건 원인과 함께 보여 줘.

[마무리]
```

## AI가 틀렸다가 고친 것 (개선 과정)

| 발견 | 처리 |
|---|---|
| 기존 끝맺음 변환이 "다릅니다"를 "다러", "바뀝니다"를 "바뀌"로 잘못 바꿈 — 새 점검의 '변환 못 한 끝맺음'에 잡힘 | 르 불규칙(달라·몰라)·ㅟ/ㅢ(바뀌어) 규칙 추가, 표에 "다릅니다·모릅니다" 행 추가 |
| 점검이 "안녕하세요, 담당자님."(인사)을 변환 못 한 끝맺음으로 셈 (180건) | 인사는 문장 끝맺음이 아니라 점검·변환 모두에서 제외 |
| 고친 뒤 "달라."(맞는 반말)가 '변환 못 한 끝맺음'으로 남음 | 점검의 반말 끝 목록에 "라·러" 추가. 점검 기준을 바꿨으므로 고치기 전 코드를 잠시 되돌려 before를 같은 기준으로 다시 측정 |
| 점검은 끝 모양만 봐서, before의 잘못된 "다러"는 '반말 모양'으로 세어져 숫자에 안 잡힘 | 숫자 밖의 오류는 사람이 결과 문장을 읽어 확인 (after에서는 "다릅니다 / 달라요 / 달라"로 바르게 나옴) |
| 수정 이유 "내 말투 설정에 맞춰…"가 동기·클라이언트(받는 사람 규칙이 먼저)에게 맞지 않음 | cards.json `reasons.byTab.mine`을 "받는 사람과 내 말투에 맞춘 문체 하나로 …"로 (콘텐츠팀 확인 필요) |

## 결과 문장 예시 (내 말투안 · 요청 방식 부드럽게)

**q01 · 선배 · 합니다체**
> 선배님, 여쭤볼 게 있습니다.
> A사 매출 증빙 표본 테스트 조서를 작성 중입니다. 먼저 표본 40건 중 35건의 세금계산서와 입금 내역을 대사했습니다. 다만 5건은 기말 직후 인도된 건이라 매출 귀속 시기를 판단하기 어렵습니다. 선택지는 ① 인도 시점 증빙을 추가 요청 ② 예외 사항으로 기록하고 다음 절차 진행입니다. 제 판단으로는 컷오프 이슈일 수 있어 ①이 맞다고 생각합니다.
> 인도 시점 증빙은 클라이언트에 직접 요청해도 될까요?

**q01 · 선배 · 해요체**
> 선배님, 여쭤볼 게 있어요.
> A사 매출 증빙 표본 테스트 조서를 작성 중이에요. 먼저 표본 40건 중 35건의 세금계산서와 입금 내역을 대사했어요. 다만 5건은 기말 직후 인도된 건이라 매출 귀속 시기를 판단하기 어려워요. 선택지는 ① 인도 시점 증빙을 추가 요청 ② 예외 사항으로 기록하고 다음 절차 진행이에요. 제 판단으로는 컷오프 이슈일 수 있어 ①이 맞다고 생각해요.
> 인도 시점 증빙은 클라이언트에 직접 요청해도 되나요?

**q03 · 동기 (반말 고정)**
> 물어볼 게 있어.
> 내부회계관리제도 통제 테스트 조서를 처음 작성하고 있어. 먼저 지난해 조서를 참고하고 감사 가이드 문서도 읽어봤어. 근데 통제 빈도에 따라 표본 수를 어떻게 정하는지 헷갈려. 선택지는 ① 통제 빈도별 가이드 표본 수 사용 ② 지난해와 동일하게 사용이야. 통제 빈도가 달라졌을 수 있어 ①이 맞다고 생각해.
> 혹시 표본 수를 어떤 기준으로 정했는지 알려줄 수 있어?

**r05 · 클라이언트 · 해요체 설정 (합니다체 고정)**
> 안녕하세요, 담당자님. 요청드릴 사항이 있어 연락드립니다.
> 수요일 15시 중간 감사 미팅을 다른 시간으로 옮기고 싶습니다. 같은 시간에 내부 필수 교육이 잡혀 참석이 어렵습니다. 기한은 오늘 중 회신입니다. 필요한 결과는 변경된 일정 초대장입니다. 목요일 오전이나 수요일 17시 이후라면 가능합니다. (상대 확인: 필요 (참석자 전원))

## 남은 한계 (실제 AI 연결 때 참고)

- 표·규칙에 없는 끝("~죠", "~네요", "~거든요" 등)이 샘플 밖 입력에 나오면 바꾸지 않고 '변환 못 한 끝맺음'으로만 표시된다 → 목록을 보고 `TONE_TABLE`을 늘린다.
- 반말로 바꿀 때 문장 속 높임("~주셔도", "~하시면")은 끝맺음이 아니라 그대로 남을 수 있다.
- 해요체의 "~주세요."는 표대로 두었다(합니다체만 "~주실 수 있을까요?"). 선배에게 "알려주세요."가 짧게 느껴지면 표의 해요체 칸을 바꾸면 된다.
- 점검은 끝 모양만 본다. 끝이 반말 모양이어도 틀린 말("다러")은 사람이 읽어야 잡힌다.
