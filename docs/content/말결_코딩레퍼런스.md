# 말결 코딩 레퍼런스 (콘텐츠·데이터팀 최준성)

> 삼일회계법인 2026 Discover A-2조 · 빌드팀 전달용 · 2026-10-05

빌드팀이 Claude로 앱을 만들고 고칠 때 따를 기준을 한 파일에 담았습니다.
샘플 데이터(전세민)와 UI 레퍼런스 수집 자료(이은서)는 각자 올린 파일을 함께 참고합니다.

## 이 파일 쓰는 법

1. Claude 프로젝트 "말결"의 **파일** 칸에 이 파일을 올립니다. (전세민 님 샘플 데이터, 이은서 님 레퍼런스 PDF도 같이 올리면 좋습니다)
2. 아래 **1장 프로젝트 지침**의 박스 안 내용을 프로젝트 **지침(Instructions)** 칸에 붙여 넣습니다.
3. 이후 Claude에게 이렇게 요청하면 됩니다: "코딩 레퍼런스 5장의 B1~B4를 2장 design 기준대로 고쳐줘."
4. Claude Design을 쓸 때는 3장 디자인 토큰을 복사해 첨부합니다.

## 목차

1. 프로젝트 지침 (지침 칸에 붙여 넣기)
2. design (UI 기준서)
3. 디자인 토큰 (Claude Design용)

5. 빌드팀 수정 요청 · 테스트 체크리스트

## 1. 프로젝트 지침

아래 박스 안 내용을 Claude 프로젝트 지침 칸에 그대로 붙여 넣으세요.

```text
너는 삼일회계법인 2026 Discover A-2조의 웹앱 "말결"을 함께 만드는 개발 파트너다.

■ 앱 한 줄 소개
말결은 신입 회계사가 선배·인차지·동기·클라이언트에게 질문·부탁·상황보고를 할 때,
① 말할 내용을 먼저 구조화하고 ② 의도는 지킨 채 내 말투로 표현하고 ③ 왜 그렇게 바꿨는지 보여 주는 웹앱이다.
"AI가 대신 말해주는 앱이 아니라, 더 잘 말할 수 있게 도와주는 앱"이다.

■ 첨부 파일과 우선순위 (충돌하면 위에 있는 파일을 따른다)
1. 코딩 레퍼런스 2장 design — 화면·컴포넌트·색·문구·메시지 생성 규칙의 기준
2. 코딩 레퍼런스 4장 카드 데이터(cards.json) — 상황 카드 3개의 입력 항목, placeholder, 되묻기 문구, 받는 사람, 말투 옵션, UI 문구
3. malgyeol_sample_data.json (전세민) — 카드별 샘플 10건씩 총 30건 (테스트·시연용 가짜 데이터)
4. 말결_UI레퍼런스_수집자료.pdf (이은서) — 참고 서비스와 화면별 컴포넌트 선택 이유

■ 반드시 지킬 것
- 화면은 4개: 홈 → 구조화 확인 → 결과 → 내 말투. 화면을 늘리지 않는다.
- 색·폰트·버튼 문구는 2장 design과 4장 카드 데이터의 uiCopy를 그대로 쓴다. 임의로 바꾸지 않는다.
- 문구를 바꿀 때는 코드가 아니라 4장 카드 데이터(cards.json)를 고친다.
- 구조화(AI 호출 1): 사용자의 한 줄에서 알 수 있는 칸만 채우고, 모르는 칸은 null로 둔다. 지어내지 않는다.
- 메시지 생성(AI 호출 2): 비어 있는 칸의 내용(특히 요청·기한·판단)을 문장에 추가하지 않는다.
  질문 준비실은 "묻고 싶은 것"을 반드시 메시지에 담는다.
- 의도 체크: AI가 항목별 근거 구절을 반환하고, 그 구절이 본문에 실제로 있는지 코드로 확인해 ✓/△를 표시한다.
- 수정 이유는 실제로 채운 칸만 근거로 2~3줄 쓴다.
- 저장은 localStorage만 쓴다. 로그인·서버 저장·메신저 전송은 만들지 않는다.
- 'A사', 'X원' 같은 마스킹 표현은 그대로 유지한다. 실제 회사명·금액·개인정보를 샘플에 넣지 않는다.
- 모바일 우선(최대 폭 480px). PC에서도 깨지지 않아야 한다.

■ 작업 방식
- 수정 요청을 받으면 "유지할 것 / 바꿀 것"을 먼저 짧게 정리한 뒤 코드를 고친다.
- 바꾼 내용은 마지막에 한두 줄로 요약해 준다 (decision-log와 기획안 P.13 근거로 쓴다).
```

> **원칙**: 이미 잘 구현된 부분은 그대로 문서화하고, 고칠 부분은 `▶ 변경` 으로 표시했다.

### 0. 한 줄 원칙

**"문장보다 구조가 먼저 보이는 앱."**
- 화면마다 사용자가 할 일은 하나, 주 버튼(파란색 채움)도 하나
- AI가 대신 써 주는 느낌이 아니라 *내가 정리하고 고르는* 느낌
- 입력은 짧게, 고르기는 쉽게, 바뀐 이유는 짧게 (레퍼런스 수집 3원칙)

| 요소 | 내용 |
|---|---|

| 필드 | `cards.json`의 `fields` 순서. AI가 채운 값은 그대로 표시, 비어 있는 필수 칸은 노란 강조 + 되묻기 |

| 버전 탭 | 내 말투안 · 더 간결하게 · 더 부드럽게 |
| 본문 | 편집 가능 |
| 의도 체크 | "확인한 내용이 메시지에 남아 있는지 살펴봤어요. 본문을 고치면 다시 확인해요." + 채운 필드별 ✓/△ |
| 수정 이유 | 2~3줄 |
| 버튼 | [복사] 주 버튼 · [다시 만들기] · [이 표현을 내 말투에 반영] · [구조 수정] |
| 복사 후 | ▶ 변경: [복사] 버튼이 2초간 **"✓ 복사됐어요"** 로 바뀌었다가 돌아오기 |

| 요소 | 내용 |
|---|---|

| 하단 | [← 홈으로] [질문으로 다시 설정] |

### 6. 메시지 생성 규칙 (프롬프트에 반드시 포함)

1. **입력에 없는 요청·판단·기한을 추가하지 않는다.** 비어 있는 칸은 문장에서도 빠져야 한다.
   - 예: `도움 요청` 칸이 비었으면 "확인 부탁드립니다" 같은 요청 문장을 붙이지 않는다.
2. **질문 준비실은 `묻고 싶은 것`을 마지막 문장에 그대로 담는다.** 질문이 없는 질문 메시지는 실패다.
3. **받는 사람별 호칭과 거리감**
   | 받는 사람 | 호칭 | 거리감 |
   |---|---|---|
   | 선배 | 선배님 | 존댓말, 바쁜 상대를 배려 |
   | 인차지 | 인차지님 / 이름+님 | 보고 위주, 결론 먼저 |
   | 동기 | 호칭 생략 가능 | 반말 허용, 짧게 (샘플 q03·q04 참고) |
   | 클라이언트 | 담당자님 | 가장 격식, 회사 대 회사 표현, 내부 용어 금지 |
4. **수정 이유는 실제로 채운 칸만 근거로** 쓴다. 비어 있는 칸을 언급하지 않는다.
5. 마스킹 표현('A사', 'X원')은 그대로 유지한다.

### 7. 시연 흐름 (1~2분)

1. 홈 → **질문 준비실** → "재고평가충당금 계산이 안 맞는데 선배한테 물어보고 싶어요" → [정리하기]
2. ②에서 AI가 상황·막힌 지점을 채우고, 빈 "해본 것"을 노란 칸으로 되물음 → 보충 → [메시지 만들기]
3. ③에서 탭 비교 → 의도 체크 ✓ → 수정 이유 → [복사]
4. ④에서 요청 방식을 "매우 조심스럽게"로 바꾸고 [다시 만들기] → 같은 의도, 다른 말투
